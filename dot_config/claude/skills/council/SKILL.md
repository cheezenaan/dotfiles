# council

相補的な設計哲学を持つ固定メンバーが審議し、前提と設計判断を検証する。
単一視点では見えない死角を、哲学の衝突から炙り出す。

diff の正しさの確認は /code-review へ。本スキルは課題設定と設計判断を疑うときに使う。

## パネル定義

メンバー構成とプロンプトテンプレートは `references/` のパネル定義ファイルにある。

- `references/software-design.md`：ソフトウェア設計とアーキテクチャ（デフォルト）

パネル定義を読み、テンプレートをそのまま使う。

## レビュー実行手順

### 1. レビュー対象の確認

ユーザーが指定した対象（ファイル、diff、設計書、ADR など）を読み取る。
指定がなければ `git diff` と `git diff --cached` で変更内容を取得する。

### 2. プロンプトの構築と実行

深い推論が必要なため上位モデルを使う（現在は `model: "fable"`）。
Agent を起動し、パネル定義のテンプレートを渡す。

テンプレートには引き算、イシュー度、ゼロベース、可逆性の4つの問いが組み込まれている。
これらを入れないと評議会レビューが足し算バイアスに陥る。

### 3. 結果の検証

メンバーの「〜は不要」「〜は解決済み」系の主張は、コード、ログ、テストで反証を試みてから採用する。
「存在しない」で止まらず、なぜ存在しないのかを問う。別の仕組みや設定、フックが既に解決していないかまで掘る。

指摘が多い場合は可逆性に基づいて優先順位をつける。

## やってはいけないこと

- メンバーの数を増やさない。各レビュアーが指摘を足すだけで誰も引き算しなくなる
